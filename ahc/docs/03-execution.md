# 4時間の進め方・失敗の診断・学習の位置づけ

[入口へ戻る](README.md) · [設計手順](01-design.md) · [事例集](02-patterns.md) · [テンプレ対応](04-template-map.md)

以下の時間配分・採用基準は準備用の提案。得点や順位の保証ではない。

## 1. AHC073向けの時間配分案

開催時間は [公式ページ](https://atcoder.jp/contests/ahc073) の **2026-10-17 15:00〜19:00 JST**。提出間隔は5分必要。

| 時刻 | 到達点 | その段階で決めること |
|---|---|---|
| 15:00〜15:10 | 問題・スコア・制約の整理 | 探索変数の候補を2つまで出す |
| 15:10〜15:35 | 検証可能な初期解と最初の提出 | 必須条件、操作上限、入出力を通す |
| 15:35〜16:15 | 乱択貪欲か局所改善が動く | 得点を失う原因を可視化、主手法を1つ選ぶ |
| 16:15〜17:30 | ビームまたはSAの主改善 | 状態・評価・近傍を1要素ずつ改善 |
| 17:30〜18:15 | よく負ける入力の原因を1つ直す | 初期解の別系統、修復近傍、終盤処理など |
| 18:15〜18:35 | 採用候補を絞る | 同じケースで比較、実行時間と失敗率を見る |
| 18:35〜18:50 | 大きな変更を止め、再提出 | 本番の設定・コンパイル・出力を確認 |
| 18:50〜19:00 | 提出結果と残余の確認 | 5分間隔を考慮。新規設計を入れない |

最初の合法解に時間がかかる問題では、この表をずらす。**動く解を保存したまま、1つの仮説を試す**ことを優先する。

## 2. 仮説を「コードを書く前」に1行にする

| 観測 | 試す仮説 | 確認する数字 |
|---|---|---|
| 近い対象ばかり取って遠方が残る | 終盤到達不能になる対象の優先度を上げる | 未達対象数、残距離、得点差 |
| ビームが同じ方面へ集中 | 同点付近で領域・資源別に枠を残す | 異なる初手/終点/資源帯の数 |
| SAで大きな構造が変わらない | 近接した対象をまとめて外して挿し直す | 同一解復帰率、改善回数/秒 |
| 点が増えたのに出力で悪化 | 近似評価が衝突・待機を無視している | 近似点とリプレイ点の差 |
| 特定の入力だけ極端に負ける | 密度・予算・日数などで原因が分かれる | パラメータ帯ごとの改善/悪化 |

「焼きなましを強くする」は広すぎる。「施設を1個消して担当を再割当すると、余計な施設が減る」のように書く。

## 3. 比較の最小セット

開発用ケースを少数固定し、別の未調整ケースも残す。候補AとBを**同じ入力・同じ計算予算**で比較する。乱数ぶれが大きいときは複数の探索seedも揃える。

| 見るもの | 目的 |
|---|---|
| 合法率、WA/RE/TLE数 | 平均点に埋もれる失敗を見つける |
| 各ケースのスコアと差 | どの入力で改善したかを把握する |
| 勝ち・引分・負け、平均改善率 | 一部の大勝だけで判断しない |
| 最大実行時間、重いケースの傾向 | 制限時間の余裕を判断する |
| 探索回数、無効率、受理率 | 手法と実装のどちらが止まっているかを分ける |

相対スコアなら、手元のベースライン比は比較用の代理指標。対戦相手の最良値が未知なので、本番の相対順位そのものは計算できない。ゼロ点を含む比率は別処理する。

パラメータを何度も合わせたケースは、もう未調整の検証ケースではない。1ケースだけの「神seed」を本番採用の理由にしない。

## 4. 症状からの診断表

| 症状 | 最初に疑うこと | 次の小さな修正 |
|---|---|---|
| 初期解が合法にならない | 全体を同時に決めすぎている | 1個ずつ・領域固定・制約の強い順で構成 |
| 貪欲が終盤で詰む | 今の利益だけを見ている | 帰還/到達余裕、残り選択肢、最小必要資源を入れる |
| 多スタートで同じ解になる | 乱数が同点処理にしか入っていない | 根・構成順・候補集合を変える |
| ビームが貪欲より弱い | 評価が不適切、良い枝が途中で消える | 貪欲完成解を別保存し、両者の良い方を返す |
| ビームが幅を増やしても同じ | 候補が少ない/偏る、同一構造が枠を占める | 上位候補に別基準や領域別候補を足す |
| 同じhashで違う将来になる | 状態に資源・履歴要約が足りない | 将来の合法手/報酬を変える変数を追加 |
| 時間切れで未完成を返す | 途中状態と提出可能解を混同 | 先に完成解保存、途中からの貪欲補完 |
| SAのほとんどが無効 | 制約を壊す編集が多い | 合法な候補を生成、または修復込みの近傍 |
| SAが受理されるのに変わらない | 修復が元の解を作る、対称変数の入替だけ | 修復順/壊す範囲/探索表現を変える |
| SAで悪化が全く通らない | 温度とdeltaの尺度が不一致 | 代表的悪化幅dと目標受理確率pから T=-d/log(p) |
| SAが終盤まで乱れる | 終温度が高い、大きな近傍が支配 | 近傍別のdeltaを見て、小近傍で仕上げる |
| 差分点だけ良くなる | rollback・キャッシュ・重複計上の不整合 | 小ケースで毎回全再計算と照合 |
| 一部ケースでだけ極端に遅い | 候補数、再構築回数、失敗時処理が増える | 入力依存の上限と途中打切りを入れる |
| 現在点が良いのに将来負ける | 資源、選択肢、投資回収を無視 | 比較可能な時刻/深さに揃え、短いrolloutを試す |

## 5. 新しい手法を止める目安

- **15〜20分で合法な1遷移が作れない**: 表現か制約処理を簡単にする。既存解の後半だけを改善する案へ戻す。
- **評価が全ケースほぼ同点**: ビーム幅・温度を調整する前に、評価の台地と残り価値を調べる。
- **20〜30分の検証で伸びる入力の理由が説明できない**: 最後に安定していた版を残し、主解法への統合を保留する。
- **残り30分で初めての大規模変更**: 習熟した局所修正以外は次回へ回し、提出済みの動く版を確認する。

これらは固定ルールではなく、4時間で検証可能な範囲に収めるための目安。

## 6. ビーム・SAから学習へつなぐ場合

### 最初に必要なのは、問題ごとの接続部分

学習ループが汎用でも、次は出題後に人間が定義する必要がある。

| 接続部分 | 決める内容 |
|---|---|
| 状態/観測 | 将来に必要な情報。未知情報を混ぜない |
| 行動 | 1移動、対象選択、挿入位置、修復対象など |
| 合法手 | 行動マスク、修復、終了の扱い |
| 遷移・報酬 | シミュレータ、最終点と中間報酬の関係 |
| 特徴量 | 大きさ・番号・回転などへの扱い、正規化 |
| 出力・評価 | 学習側と提出C++側で同じ結果が出ること |

**良い初期解を作る難しさは、学習器を用意しても自動では消えない。** まず、手書きの状態・合法手・評価器・構成器を完成させる。

### 教師データと強化学習を区別する

ビーム/SAの良い解から行動を再生して教師にする段階は、模倣学習として設計できる。完成解だけでは、各状態でどの行動が合法だったか、別の行動よりどれだけ良いかまでは分からない。SAで編集した最終順列も、必要なら合法な実行列へ復元してから使う。

報酬を得ながら方策を更新する段階では、教師が訪れなかった状態への対応、合法手マスク、疎な報酬、探索時と本番時の分布差を扱う。開発の残り時間にはデータ生成・学習・検証・モデル変換も含める。提出プログラムではモデル読込・推論・探索の合計を制限時間内に収め、同じ提出時間を非学習のビーム/SAに使ったベースラインとも比較する。

短期では、既に動く環境がない限り主戦力に据える判断は重い。小さな検証で費用対効果を示せるなら、まずは候補順位付けや少数パラメータ推定など、影響範囲の狭い使い方を検討する。これは準備時点の技術上の判断であり、本番利用の規則上の許可を意味しない。

### 開始前に確認する運用

事前生成コードの公開・提出時URL、開催中の生成AI使用については [入口の規則メモ](README.md#今日の事前準備) と [公式本文](https://info.atcoder.jp/entry/short-ahc-llm-rules-ja) を参照。非生成AIのパラメータ最適化は規則に例示されているが、自作RL全般の可否まで一律に断定しない。LLMが問題・実行結果を読んで修正する自動ループと、自前の数値学習は区別して確認する。

## 7. 最終出力の確認

1. 探索中の近似評価とは別に、**実際に出力する解**を最初からリプレイする。
2. 個数、座標範囲、重なり、連結、先行関係、予算、手数上限など、問題の必須条件を見る。
3. 制限時間は探索だけでなく入力・復元・出力・メモリ解放も含めて余裕を残す。
4. 最小化/最大化の向き、最良完成解の保存、時間切れ時の返却先を確認する。
5. デバッグ出力は標準エラーへ。対話型ならflush、応答読込、終了条件を確認する。

「最初の解」「最後に採用した解」「いま実験中の解」がすぐ識別できる名前で保存されていると、終盤の判断が楽になる。
