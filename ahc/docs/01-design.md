## 1. 完成解の価値と、途中状態の価値を分ける

仮に「異なる種類を多く集め、同じ種類の追加取得にも少し価値がある」なら、完成解では種類数と個数を正しく評価する。一方、構築途中では、今の種類数が少なくても、未取得の種類が密集する場所にいて燃料を残している状態に価値がある。

途中評価は、たとえば次の分解で考える。

$$
V(s)=\text{確定した利益}+\text{残りで獲得できる利益の見積り}-\text{将来の制約違反リスク}
$$

「残燃料に何点」「終点に何点」と先に係数を作るより、**その残燃料・終点で、追加で何を達成できるか**を見積もる方が意味を保ちやすい。安い貪欲で最後まで完成させた値も、途中評価の有力な候補になる。

### 目的の優先順位を読み違えない

公式が辞書順評価なら、まずその順序を守る。独自に `大きい係数 × 主目的 + 副目的` にする場合、係数を適当に決めると優先順位を壊し得る。主目的が整数で最小の差が 1 なら、副目的の取り得る最大差より係数を大きくすれば優先順位を保てる。主目的が連続値の場合は同じ保証をそのまま使えない。安全な係数を決められないならタプルで比較する。

公式スコアが単調変換されている場合、**一つの入力で解を比較するだけなら**変換前の量で比較できることがある。ただし複数入力の平均・合計の比較では、変換を外すと重みが変わる場合がある。コンテスト全体の集計方法と、入力一つの最適化を分けて考える。

## 2. 厳しい制約から表現を決め、細部を復元器へ任せる

「最後に合法か検査する」構造より、「操作すると自然に合法になる」構造にできないかを先に考える。

- 必ず全要素を一回ずつ使う → 順列。
- 各仕事をどれか一台に担当させる → 割当＋各台の順序。
- 全点を接続する → 木や、必須の接続構造を保持する表現。
- 先行関係を守る → 実行可能な仕事だけ選ぶ decoder、またはトポロジカル順序。
- 配置の重なりが難しい → 挿入順を探索し、decoder が合法な位置を選ぶ。
- 移動の細かい手順が長い → 訪問順・経由点・作業順を探索し、経路を復元する。

こうして細部を復元器に任せると、探索が判断すべき変数を減らせる。ただし decoder が表現できない解は探索しても出てこない。最初は単純な decoder で動かし、伸びが止まったら「この復元規則で最適そうな解を作れるか」を疑う。

混合問題では、一つの表現に全部入れない方が作りやすい。例として、**担当割当は局所探索、担当内の順序は挿入法、移動経路は最短路**という分解がある。どこまで厳密に解き、どこをヒューリスティックにするかを決める。

探索対象を選ぶときは、以下を一度確認する。

- 直接動かす変数は何か。順序だけで十分か、採用集合や担当も変える必要があるか。
- その変数を与えれば、合法な完成解を短時間で作れるか。
- 一変数の変更が、局所だけを変えるか、後半全体を変えるか。
- 自分が手で考えた有望な解を、その表現と復元器で作れるか。

## 3. 最低点を確保しつつ、改善につながる貪欲を作る

### 3.1 「一番近い」から一段進めるための六つの軸

| 見るもの | 具体的な問い | 効きやすい場面 |
|---|---|---|
| 限界利益 | それを足すと本当に何点増えるか | 被覆、種類収集、重複価値の小さい問題 |
| 限界コスト | 既存の解に差し込むと何が何単位増えるか | 経路、配送、加工順序 |
| 希少性 | これを後から達成する方法は何通りあるか | 担当可能者が少ない仕事、孤立した需要 |
| 後悔値 | 最良の割当を逃すと、二番目でどれだけ損するか | 挿入位置や担当の選択 |
| 将来の自由度 | その一手で、次の合法候補はいくつ残るか | 詰みやすい配置、盤面操作、容量制約 |
| 終了時の余裕 | 帰還・接続・締切のために何を残す必要があるか | 移動、バッテリー、最後の必須処理 |

追加コストが非負なら、`追加利益 / (追加コスト + 小さい正数)` を出発点にできる。ただしゼロコストや非常に小さいコストで比が極端にならないようにする。比率だけでは大きい一手が負けるので、追加利益最大・希少性優先など、異なる基準も少数用意する。

**後悔値の小例**：二つの仕事を、各機械に一件ずつ割り当てる。費用は、仕事 A が機械 1 なら 3、機械 2 なら 20。仕事 B は機械 1 なら 2、機械 2 なら 4。費用最小の組から決めると B を機械 1 に置いて合計 22 になる。一方、A が機械 1 を逃す損は 17、B は 2。損の大きい A を先に機械 1 へ置けば合計 7。このように、最良の選択肢を失った損を見る。

### 3.2 最後まで完成できるかを、選択前に見る

移動問題なら、「次に到達できる」だけでなく「その後に必須の帰還ができる」を確認する。配置問題なら、今の一つが置けるだけでなく、残り必須要素の置き場所を塞がないかを見る。厳密に確認できない場合も、帰路の下界、残容量、未接続成分の接続コストといった安い必要条件は作れる。

これにより、初期解を一度作ってから全面修復する場面を減らせる。ただし、楽観的な必要条件を通ったから完成可能だと断定してはいけない。

### 3.3 多開始は、構造の違う初期解を作る

同じ貪欲の点数に微小乱数を足すだけでは、同点の順番しか変わらず、担当・始点・経路の骨格が固定されたままになることがある。先に次の軸を変える。

- 始点、最初に処理する領域、最初に選ぶ施設。
- 仕事と担当の割当。
- 希少性優先、距離優先、利益優先という基準。
- 残資源の配分、担当領域の分割。
- 上位候補から確率的に選ぶ際の候補の広さ。

初期解が同じスコアでも、終点や残資源、担当が異なるなら改善後の結果は変わり得る。初期スコアだけで一つに絞るのではなく、少数を同じ短い改善にかけて比較する方法もある。

## 4. ビームサーチ：state と評価を設計する

### 4.1 「これから先を決めるために必要な情報」を state にする

最初に次の質問をする。

> 二つの履歴がこの state に一致したとき、この先の合法行動、得られる追加利益、終了条件も同じになるか？

同じなら履歴を捨てられる可能性がある。違うなら state が不足している。

仮に「燃料を使って点を訪れ、種類を集める」問題なら、候補は位置、残り時間、残燃料、取得済み種類、消費済み在庫、必要な帰還条件。全点が一度しか取れないなら、種類マスクだけでは足りず、消費した点や在庫も必要になる。時間で移動コストが変わるなら、現在時刻も必要になる。

状態には大きな履歴列を直接持たず、親への参照と最後の行動から復元できるようにする、という実装上の選択はある。ただし、何を state に含めるかという意味の設計と、メモリの持ち方は別の問題である。

### 4.2 同じ state なら必ず一つにしてよい、とは限らない

将来の合法行動・追加利益が同じで、完成値が `これまでの値 + この先の値` と分解できるなら、これまでの値が悪い方を捨てられる。

しかし、最大値・分散・コンボ・訪問履歴によるボーナスなどがあるなら、その集計情報も state に含める必要がある。また、同じ位置でも残時間・残燃料が違えば同値ではない。

**優越による枝刈り**は同値より広い。例えば、それ以外の条件が一致し、取得済み報酬が同じで、ある状態が時間と燃料をどちらも多く残しているなら、少ない方を捨てられる場合がある。ただし「時間が早い方が常によい」「燃料が多くても不利益がない」など、問題固有の単調性を確認して使う。

ハッシュは一致候補を速く探す道具であり、同値性の定義ではない。必要な変数をキーに含め、ハッシュの一致と state の一致を混同しない。

### 4.3 一手の粒度を変える

移動一歩ごとに分岐させると、肝心の「どの仕事を選ぶか」に到達する前に幅を使い切ることがある。その場合は、以下のようなマクロ行動を考える。

- 次の目的地へ移動して作業まで実行する。
- 次の仕事を一台に割り当てる。
- 一行・一区画を完成させる。
- 一回の補給と、その前後の作業をまとめる。

移動の途中に価値のある判断があるなら、すべてを最短路に固定してよいわけではない。マクロ化で落ちる選択肢と、増える探索深さを比較する。

### 4.4 候補生成は「評価上位」だけにしない

上位候補が全部同じ領域・担当になるなら、点数上位を大量に残しても判断の種類は増えない。たとえば次のカテゴリから少数ずつ生成する。

- 即時利益が大きい候補。
- 移動・時間・消費が小さい候補。
- 後から取るのが難しい候補。
- 未探索領域や将来有望な終点へ向かう候補。
- 補給・待機・帰還など、準備に当たる候補。

候補を削る前に、全候補を見たときに必要そうな一手が含まれているか確認する。**候補に出ない一手は、幅を増やしても選ばれない。**

### 4.5 可変長の行動では、「深さ」の意味をそろえる

一手が短い作業にも長い作業にもなる場合、「作業を三個選んだ状態」同士でも消費時間が大きく違う。単に現在の得点で同じビームに並べると、比較の仕方に偏りが出る。

考えられる対処は、問題に合わせて次から選ぶ。

- 処理済みの仕事数・要素数など、意味のそろう層を作る。
- 経過時間の区間ごとに候補を管理する。
- 安い rollout で全状態を終端まで完成し、その値で比べる。
- 現在値＋残り価値の推定で、共通の終了時点の価値を比べる。

「一手あたりの得点」に直せば解決するとは限らない。固定の終了条件に対して何を最大化するかに戻る。

### 4.6 中間評価は、情報を一つずつ足す

まず確定利益を基準に置く。全状態が同点になる問題では、最初から残り価値の見積りも必要になる。失敗した例で「なぜ本当はよい状態を落としたか」を見て、情報を足す。

1. 残時間・残資源で達成できそうな量の簡単な見積り。
2. 未達成の利益に、現在地からの到達コストを組み合わせる。
3. 安い貪欲 rollout による完成値。
4. 残る少数だけを DP・全探索して、終盤を正確に評価する。

最大化で、数学的に正しい上界が最良の合法な完成解以下なら、その枝を捨てられる。「楽観的に見積もった値」が正しい上界とは限らない点に注意する。また、正しい上界でも過大評価の程度は状態ごとに違うため、大きい順に並べるだけで強い選別になるとは限らない。よい評価でも一つの骨格に集中するなら、終点・残資源・未達成の種類などで少数の枠を分ける方法を考える。

## 5. 焼きなまし：表現と近傍を設計する

### 5.1 最初に答えるのは「どの解からどの解に動けるか」

温度調整の前に、次の三つを確認する。

1. 一回の提案で、意味のある部分を変えられるか。
2. 合法な提案が十分な頻度で作れるか。
3. 良さそうな別の骨格へ、その近傍を何回か使って移れるか。

たとえば、訪問する点の**順番だけ**を swap しても、訪問集合は変わらない。どの仕事をどの車が担当するかが固定なら、車内の 2-opt を何回しても担当の誤りは直らない。探索できる解の範囲を紙に書いてみる。

制約のない順列なら swap で全順列へ到達できるが、途中の合法性を強く制限すると、合法解の集合がその近傍で分断されることがある。「swap があるから十分」とは限らない。

### 5.2 近傍の一覧：小さな変更と骨格を変える変更を持つ

| 表現 | 小さな近傍 | 大きな近傍・詰まりの解消 | 注意する依存関係 |
|---|---|---|---|
| 順列 | 二点交換、一点移動、短区間反転 | 連続区間移動、部分破壊して再挿入 | 先行制約、時刻、後続の状態 |
| 複数ルート | ルート内 relocate、2-opt | 他ルートへの移送、区間交換、担当の作り直し | 容量、締切、各ルートの終点 |
| 選択集合 | add、remove、1 対 1 交換 | 1 対 2、2 対 1、近い一群の入替え | 予算、重複利益、被覆の重なり |
| 割当 | 一件を別担当へ、二件交換 | 押し出された仕事を連鎖的に移す、部分再割当 | 一台だけの負荷改善が他台を悪化させる |
| 座標配置 | 少し移動、近い候補点へ移動 | 遠くへ再配置、複数施設の同時移動 | 被覆境界、衝突、最近傍担当の変化 |
| 木・接続グラフ | 辺追加＋不要辺削除 | 部分木の付替え、局所領域を接続し直す | 連結性、閉路、経路長 |
| 操作列 | 操作の変更、短い部分の再探索 | 区間を消して始終状態間を解き直す | 後続操作の前提が崩れる |

2-opt の距離差が局所だけで求まっても、燃料・時刻・先行関係の合法性まで局所で判定できるとは限らない。既存コードの式を移植できる条件は [テンプレ対応](04-template-map.md#2-opt-の式がそのまま使える条件) を確認する。

### 5.3 制約が硬いときの三つの方針

**A. 常に合法な近傍を使う。**

合法な挿入位置だけ選ぶ、木を保ちながら辺を交換する、容量内で担当を移す。違反処理が不要で、本スコアを直接使いやすい。一方、近傍が狭すぎると別のよい骨格に移れない。

**B. 順序や優先度を探索し、decoder で合法解にする。**

例えば「仕事の優先順」を探索し、decoder が先行関係と機械の空きを守って順に割り当てる。探索変数は自由に動かしやすい。ただし一つの順序変更で後半が大きく変わることや、異なる優先順が同じ解に復元されることがある。差分評価のしやすさと、表現できる解の幅を確認する。

**C. 一部を壊してから修復する。**

近い仕事、混んだ領域、長い辺の周辺などを外し、残った解に貪欲で挿し直す。外す数を変えると局所改善と大きな移動を兼ねられる。修復失敗時に元へ戻すことと、修復器の挿入順による偏りを考える。

違反ペナルティを付けて一時的に違反を許す方法もあるが、制限時間までに合法へ戻らない可能性がある。使う場合は、合法な最良解を別に保持し、違反量を段階的に減らせる評価を作る。

### 5.4 評価がゼロの台地では「達成までの距離」を作る

仮に一定以上の通信品質を満たした端末だけ加点されると、品質が 0.2 から 0.8 へ上がっても閾値が 1.0 なら得点が変わらない。

探索用には、達成済み報酬に加えて、未達成端末の閾値までの不足量、到達可能性、重み付きの部分達成を使う案がある。ただし全部を少しずつ改善して一件も達成しない方向へ誘導する危険もある。閾値の近くを重点的に評価する、途中から補助項を弱めるなど、完成解の価値へつなぐ。

最大遅延のようなボトルネック目的でも、最悪の一件が変わらないと改善が見えない。二番目以降の大きい遅延の和、上位数件の悪さ、制約の余裕を補助項として使える。**出力候補の更新は必ず本来のスコアで行う。**

### 5.5 温度を触る前に、提案の質を見る

ログでは、提案回数だけでなく、合法な提案の割合、受理率、改善回数、近傍ごとの時間と改善寄与を見る。「違反が多い」「変更しても同じ解に戻る」「悪化手が温度のため通らない」を分ける。温度の決め方、評価の尺度、時変ペナルティの注意は [テンプレ対応](04-template-map.md#温度は無次元の強さではない) にまとめている。

## 6. 差分評価と rollback：どこまで再計算するか

速さは探索回数に直結するが、誤った差分は探索の判断そのものを壊す。

変更の影響範囲を、依存関係で考える。

- 辺コストの単純な和 → 変わった辺だけ。
- 被覆数 → その施設が変更前後に覆う要素だけ。
- 機械ごとの負荷の和 → 変更した担当だけ。ただし全体の最大値を別途更新する。
- 時刻依存のルート → 最初に変わった位置から後ろ。以前と同じ状態に戻ったなら途中で打ち切れる場合がある。
- 後続の燃料・在庫・衝突が変わるシミュレーション → 関係する後続へ影響を伝播する。

安全な作り方は、最初に全再計算版を動かして基準にし、重い箇所が見えたら差分化すること。デバッグ時に、一部の提案について全再計算と差分値を突き合わせると、探索結果が悪い原因をアルゴリズムと計算ミスに分けやすい。

rollback は、配列を戻すだけでは足りない場合がある。キャッシュ、被覆数、最大値管理、ハッシュ、資源量など、その提案で変えた情報をすべて戻す。復元が難しければ、小さい state のコピーや、影響部分だけの退避から始める。

## 7. 小さな設計例：同じ問題をどう分解するか

### 例 A：燃料制限のある、種類収集の移動

**決定**：訪問集合、訪問順、必要なら担当車両。道路上の一歩ずつは、まず経路復元器に任せる。

**初期解**：未取得の種類への追加利益を、移動＋作業＋必須帰還に必要な追加コストで割って選ぶ。孤立した種類は後回しの損も見る。

**ビーム**：位置・時刻・燃料・取得済み種類・消費在庫を持つ。次のスポットへの移動と取得を一手にする。中間評価は取得済み利益＋残りで取りやすい未取得種類。補給や帰還を候補から落とさない。

**焼きなまし**：訪問順だけでは訪問集合を改善できないので、挿入・削除・置換を持つ。複数車両なら担当移送も持つ。燃料違反を避けるには、decoder が実行可能な訪問を採用する方式や、経路の一部を外して挿し直す方式を検討する。

**落とし穴**：種類数が同じなら、終点・燃料・最後の未取得種類へのアクセスが違っても同点になる。構築途中の評価には残りの見込みが必要。また、追加取得を優先したために、必須の遠い一種類を永久に先送りする場合がある。

### 例 B：先行関係のある仕事を、複数機械へ割り当てる

**決定**：実行可能になった仕事の選択、担当機械、各機械の順番。

**初期解**：先行仕事が完了した候補の中から、後続が長い仕事、担当可能機械が少ない仕事、最良担当を逃した損が大きい仕事を優先し、早く終わる担当へ割り当てる。

**表現の候補**：優先順位＋decoder なら、先行関係を守る復元器に合法性を任せられる。機械ごとの順序を直接持つなら、変更による循環や先行関係の破壊に注意する。

**改善**：ボトルネック機械の一件を別へ移す、二件交換する、遅延の大きい周辺を部分的に再割当する。最大完了時刻だけで台地になるなら、上位数台の完了時刻も探索の補助情報にする。

**落とし穴**：仕事一つを短い機械へ移しても、その仕事の後続が遅れて全体が悪化する。担当単体の所要時間だけで差分を決めない。

### 例 C：予算内で施設を配置して需要を覆う

**決定**：施設数、場所、強度やサイズ。必要なら施設間の接続。

**初期解**：すでに覆った需要を除き、追加被覆利益÷追加費用で施設を置く。必須接続があるなら設置費だけでなく接続費も見る。

**改善**：小移動だけでなく、施設を一つ消して別地域へ置く、二つをまとめる、一つを二つに分ける、近い一群を作り直す。数を変えることが重要な問題なら、固定数の座標移動だけでは足りない。

**落とし穴**：被覆の重複が大きいと、各施設が単独で覆う人数を足しても本スコアにならない。担当や被覆数を維持し、限界利益を評価する。

## 8. 未知情報・オンライン問題なら、推定と最適化を分ける

未知の処理時間や能力がある場合、まず次のループを別々に設計する。

1. 観測から何を推定するか。
2. 今の推定で、次の行動をどう選ぶか。
3. その行動後の観測で、どう推定を更新するか。

初期の推定精度が低い段階で長い計画を固定すると、見積りの誤差が積み重なる。実行は短い区間にし、観測後に再計画する方法が考えられる。

「今すぐの利益が低くても、未知の値がよくわかる行動」に価値がある。ただし情報を集めること自体を目的化せず、残り期間でその情報を使って回収できるかを見る。終盤ほど、情報獲得より既知のよい行動を使う価値が高くなりやすい。

推定値ぴったりに資源を使い切る案は、誤差で破綻しやすい。安全マージン、悲観寄りの処理時間、少数のシナリオでの評価などを候補にする。どの程度保守的にするかは、失敗の損失と余裕の費用を比べて決める。

不確実性がある箇所を巨大な state に何でも詰める必要はない。まず平均・ばらつきなど、次の判断を変えるための情報を持つ。問題の観測モデルがわかってから、必要な精度へ上げる。

## 9. 手法の組合せと、残り時間の判断

各段の役割を一行で説明する。貪欲で合法解、ビームで構築の大きな選択、SA で完成解の集合・順序・割当の改善、部分問題を DP・最短路で修復、という組合せは考えられる。すべてを使う必要はなく、今の失敗の原因を直す段だけを選ぶ。

ビーム・SA の解を使う学習も、**何の判断を学び、何を速くするか**が決まって初めて設計になる。汎用テンプレだけでは問題固有の観測・行動・合法性・報酬は確定しない。[学習の位置づけ](03-execution.md#6-ビームsaから学習へつなぐ場合) を参照。

[時間配分](03-execution.md#1-ahc073向けの時間配分案) と [撤退の目安](03-execution.md#5-新しい手法を止める目安) も別ページにまとめた。動く解を保存し、次の変更で直す欠点を一つ決め、同じ入力・同じ計算予算で比較する。
